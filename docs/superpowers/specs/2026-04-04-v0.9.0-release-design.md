# Visio Mobile v0.9.0 — Release Design Spec

**Date:** 2026-04-04
**Issues:** #192, #193, #194, #195, #196, #197, #198, #199, #200, #201, #202, #203
**Strategy:** Approche A (layout piloté par le Core), branching par phase (5 PRs)

---

## Overview

La v0.9.0 transforme Visio Mobile en client performant pour les grands groupes (10-100+ participants) en ajoutant un moteur de layout intelligent, la gestion de souscription vidéo, et en stabilisant les fondations (Bluetooth, reconnexion, initialisation). La release inclut aussi le chiffrement chat, les feature flags, l'automatisation i18n, et les tests visuels.

### Architecture Decision: Layout piloté par le Core

Toute la logique de tri, pagination, et souscription vidéo vit dans `visio-core` (Rust). Les UIs natives (Android/iOS/Desktop) sont des renderers qui:
1. Informent le core de l'état d'affichage (page_size, page courante, orientation)
2. Reçoivent des listes pré-triées et des événements de changement
3. N'interagissent jamais directement avec l'API LiveKit de souscription

Justification: cohérent avec l'architecture existante (BandwidthController est dans le core), logique partagée testable en Rust, pas de duplication Android/iOS.

### 1a. #203 — Bluetooth audio routing reliability

#### Android — 3 corrections

**1. Restart AudioTrack/AudioRecord sur changement BT mid-call**
- Fichiers: `android/.../AudioCapture.kt`, `android/.../AudioPlayout.kt`
- Aujourd'hui `setPreferredDevice()` est appelé sur une instance déjà en cours — pas fiable
- Nouveau flow: `stop()` → `setPreferredDevice(newDevice)` → `start()`
- Encapsuler dans une méthode `switchDevice(device)` sur chaque classe

**2. Debounce SCO dans ContextDetector.kt**
- Fichier: `android/.../ContextDetector.kt` (lignes 177-260)
- Les `AudioDeviceCallback` et `BroadcastReceiver` peuvent fire avant que le profil SCO soit établi
- Ajouter un listener sur `BluetoothHeadset.ACTION_CONNECTION_STATE_CHANGED` avec `STATE_CONNECTED` comme confirmation
- Ne router l'audio qu'après ce signal. Timeout 3s — si pas de confirmation, ignorer l'événement

**3. Debounce rapide connect/disconnect**
- Si connect/disconnect arrivent à <500ms d'intervalle, ne traiter que le dernier événement

#### iOS — 1 correction

**4. Gestion du gap A2DP → HFP**
- Fichiers: `ios/.../AudioPlayout.swift`, `ios/.../Services/ContextDetector.swift`
- Écouter `AVAudioSession.routeChangeNotification` avec reason `.routeConfigurationChange`
- Pendant la transition (absence de port BT output dans la route alors qu'un device BT est connecté): fallback temporaire sur le speaker intégré
- Quand HFP établi (port BT réapparait): re-router vers BT
- Pas de buffering — le fallback speaker suffit pour 200-500ms

**Tests:** Tests manuels uniquement (BT nécessite matériel). Scénarios documentés dans la PR.

### 1b. #193 — Reconnexion robuste

**Fichier principal:** `crates/visio-core/src/room.rs`

**1. `prepare_connection()` avant `connect()`**
- Requête HTTP HEAD sur l'URL LiveKit WebSocket (timeout 5s)
- Si échec → erreur `VisioError::NetworkUnreachable`
- Exposé via UniFFI pour feedback UI "Vérification de la connexion..."

**2. Réduction des tentatives**
- 10 → 3 tentatives, backoff 800ms / 1.6s / 3.2s
- 10 tentatives = jusqu'à 5 min d'attente, trop long sur mobile

**3. Cache du token LiveKit**
- Stocker `(token, url, timestamp)` après `connect()` réussi dans `RoomManager`
- `reconnect()`: si token < 5 min → réutiliser. Si > 5 min → re-fetch via API

**4. Timeouts différenciés**
- `connect_timeout`: 60s → 20s dans `create_room_options()`
- Ajouter timeouts publication/souscription tracks via options LiveKit

**5. Re-sync post-reconnexion**
- Après événement `Reconnected`: re-fetch participants depuis la Room LiveKit
- Comparer avec état local, émettre `ParticipantJoined`/`ParticipantLeft` manquants

**Tests:** Unitaires sur cache token (expiration, invalidation). `prepare_connection()` testable avec mockito.

### 1c. #195 — Initialisation à phases explicites

**Fichiers:** nouveau `crates/visio-core/src/init.rs`, `crates/visio-ffi/src/lib.rs`, `visio.udl`

#### Phases

| Phase | Nom | Contenu | Peut échouer? |
|-------|-----|---------|---------------|
| 1 | Settings | SettingsStore (display name, langue, thème, instances) | Corruption config uniquement |
| 2 | Auth | Restauration session OIDC/cookie | Oui (token expiré) → continue en non-auth |
| 3 | Services | Calendar sync, feature flags | Chaque service échoue indépendamment |

#### API UniFFI

```
enum InitPhase { "Settings", "Auth", "Services", "Ready" };
enum InitResult { "Success", "PartialFailure" };

dictionary InitPhaseError {
    InitPhase phase;
    string error_message;
};

callback interface InitProgressListener {
    void on_phase_started(InitPhase phase);
    void on_phase_completed(InitPhase phase, InitResult result, InitPhaseError? error);
};

// Nouveau constructeur (l'ancien sans listener reste disponible)
constructor VisioClient(string data_dir, InitProgressListener listener);
```

**Tests:** Test unitaire par phase (mock filesystem pour Settings, mock HTTP pour Auth).

## Phase 2 — Moteur de layout intelligent

**Branche:** `feat/v0.9.0-phase2-layout-engine`
**Issue:** #201 (Tri participants voice activity + anti-flicker)

### Nouveau module: `crates/visio-core/src/layout.rs`

#### LayoutEngine

```rust
pub struct LayoutEngine {
    sorted_order: Vec<String>,    // SIDs triés
    last_sort: Instant,
    layout_mode: LayoutMode,      // Grid | Speaker
    current_page: usize,          // 0-indexed
    page_size: usize,             // Fourni par l'UI
    pinned_participant: Option<String>,
    pin_time: Option<Instant>,
}

pub enum LayoutMode { Grid, Speaker }
```

#### Algorithme de tri

Critères dans l'ordre:
1. **Hand raised** → en premier
2. **Voice activity avec fenêtre anti-flicker 10s**: si A et B ont parlé dans les 10 dernières secondes → tri stable par `identity`. Sinon → tri par `last_spoke_at` descendant
3. **Camera on** avant camera off (`has_video`)
4. **Join time** ascendant (tiebreaker)

Donnée manquante: `last_spoke_at: Option<Instant>` à ajouter dans `ParticipantInfo`. Mis à jour depuis `ActiveSpeakersChanged` dans l'event loop.

Fréquence: recalcul sur chaque `ActiveSpeakersChanged` (~500ms-1s). Comparaison avec l'ordre précédent — émission de `ParticipantOrderChanged` uniquement si changement.

#### Pagination logique

```rust
fn set_page_size(&mut self, size: usize);
fn set_current_page(&mut self, page: usize);
fn visible_participants(&self) -> Vec<String>;
fn precached_participants(&self) -> Vec<String>;  // Pages ±1
fn page_count(&self) -> usize;  // ceil(total / page_size)
```

Aucun cap codé en dur. Fonctionne pour N participants (testé à 20, 50, 100+).

#### Speaker mode logique

```rust
fn main_participant(&self) -> Option<String>;
fn thumbnail_participants(&self) -> Vec<String>;
fn pin_participant(&mut self, sid: Option<String>);
```

- Main: dominant speaker avec anti-flicker 3s (ne pas changer si nouveau speaker parle depuis < 3s)
- Pin override: participant pinné reste en main jusqu'à unpin
- Thumbnails: les autres, même algo de tri

#### Modifications UDL

```
enum LayoutMode { "Grid", "Speaker" };

void set_layout_mode(LayoutMode mode);
LayoutMode get_layout_mode();
void set_page_size(u32 size);
void set_current_page(u32 page);
u32 page_count();
void pin_participant(string? sid);
```

Nouveaux événements: `ParticipantOrderChanged`, `PageChanged`, `MainParticipantChanged`.

#### Tests

- Tri: 5 participants, ordre hand-raised > voice > camera > join
- Anti-flicker: 2 participants alternent toutes les 2s → ordre stable 10s
- Anti-flicker expiration: silence 11s → descente
- Pagination: 12 participants page_size=4 → 3 pages
- Pagination: 100 participants page_size=4 → 25 pages, tri < 1ms
- Speaker main anti-flicker: changement < 3s → main inchangé
- Pin override: main fixe malgré speaker changes

## Phase 3 — Layouts mobiles

**Branche:** `feat/v0.9.0-phase3-mobile-layouts`
**Issues:** #199 (Grille paginée), #200 (Speaker mode)

### 3a. #199 — Grille vidéo paginée

#### Android — `CallScreen.kt`

- Remplacement de `OfficeGridLayout` par `HorizontalPager` (Compose Foundation)
- Chaque page = grid de `page_size` tiles (2x2 portrait, 3x2 paysage tablette, 3x1 paysage phone)
- `page_size` calculé depuis `BoxWithConstraints` → envoyé au core via `setPageSize()`
- Au swipe → `setCurrentPage(page)`
- Page indicator: dots si ≤ 8 pages, texte "3/13" sinon
- `LaunchedEffect(orientation)` recalcule page_size
- Swipe disabled en mode Car

#### iOS — `CallView.swift`

- `TabView` avec `.tabViewStyle(.page)` remplace le grid (lignes 484-580)
- `LazyVGrid` par page, `page_size` depuis `GeometryReader`
- `.onChange(of: currentPage)` → `setCurrentPage()`
- Page indicator: dots natifs si ≤ 8 pages, overlay texte sinon
- `onRotate()` → recalcul page_size

#### Desktop — inchangé

Pas de pagination. Consomme `sorted_participants()` pour le tri intelligent, ignore la pagination.

#### Transition screen share

Screen share → focus layout (existant). Arrêt screen share → retour à `current_page` conservée par le LayoutEngine.

### 3b. #200 — Speaker mode

#### Layout

- Zone principale (~70% hauteur): tile unique, `main_participant()` du core
- Thumbnail strip (~100dp, bas): `LazyRow` (Android) / `ScrollView(.horizontal)` (iOS)

#### Android

```kotlin
@Composable
fun SpeakerLayout(
    mainSid: String?,
    thumbnails: List<String>,
    participants: Map<String, ParticipantInfo>,
    onThumbnailTap: (String) -> Unit,
)
```

- Main tile: `VideoTile` existant avec `Modifier.fillMaxWidth().weight(0.7f)`
- Thumbnails: `LazyRow`, 100dp × 75dp, bordure accent sur le pinné
- Auto-scroll: suit le participant actif sauf si scroll manuel < 5s

#### iOS

```swift
struct SpeakerLayout: View {
    let mainSid: String?
    let thumbnails: [String]
    let participants: [String: ParticipantInfo]
    let onThumbnailTap: (String) -> Void
}
```

`VStack` avec main tile `.frame(maxHeight: .infinity)` + `ScrollView(.horizontal)`.

#### Toggle Grid ↔ Speaker

- Nouveau bouton dans la barre de contrôles (icône grid ↔ speaker)
- `setLayoutMode(.Grid | .Speaker)` → core émet `LayoutModeChanged`
- Défaut: Speaker si participants > 6, Grid sinon. Configurable dans Settings (`preferred_layout`)
- Screen share → focus mode (override). Arrêt → retour au mode utilisateur
- Desktop: speaker mode aussi disponible

#### Nouvelles clés i18n

```json
"layout.grid": "Grid view",
"layout.speaker": "Speaker view",
"layout.page": "Page {current} of {total}",
"layout.switchToGrid": "Switch to grid view",
"layout.switchToSpeaker": "Switch to speaker view"
```

#### Tests

- 50 participants, page_size=4 → 13 pages, dernière page = 2 tiles
- 100 participants: indicateur compact, tri < 1ms
- Toggle grid→speaker→grid: page courante préservée
- Speaker + pin: main fixe malgré speaker changes
- Screen share interrupt: speaker → focus → retour speaker
- Rotation: page_size recalculé, page ajustée (floor(old_page * old_size / new_size))

## Phase 4 — Gestion intelligente des souscriptions

**Branche:** `feat/v0.9.0-phase4-smart-subscriptions`
**Issues:** #198 (Unsubscribe off-screen), #202 (Screen share HIGH)

### Nouveau module: `crates/visio-core/src/subscriptions.rs`

#### SubscriptionManager

```rust
pub struct SubscriptionManager {
    subscribed: HashMap<String, VideoQuality>,
    pending_unsubscribe: HashMap<String, Instant>,
    pending_quality_change: HashMap<String, (VideoQuality, Instant)>,
}

pub enum VideoQuality { High, Low, Off }
```

#### Matrice de décision

| | Full | ReducedVideo | AudioOnly |
|---|---|---|---|
| Screen share | HIGH | HIGH | Off |
| Visible (page courante) | HIGH | LOW | Off |
| Pre-cached (pages ±1) | LOW | Off | Off |
| Off-screen | Off | Off | Off |

Audio tracks: toujours souscrites (pas de gestion côté subscription manager).

#### Anti-jitter

| Transition | Délai | Justification |
|---|---|---|
| Visible → Off-screen (unsubscribe) | 2s | Éviter flash noir au swipe rapide |
| Visible → Pre-cache (HIGH→LOW) | 5s | Éviter yo-yo entre pages adjacentes |
| Off-screen → Visible (subscribe) | 0s (immédiat) | L'utilisateur veut voir maintenant |

Tick de vérification: `tokio::interval` 500ms pour traiter les pending timeouts.

#### Screen share exception (#202)

Screen share toujours HIGH sauf en AudioOnly. Bypass les délais anti-jitter. Multi screen-share: toutes souscrites (rare, temporaire, dynacast limite le coût).

#### Orchestration dans RoomManager

```
ActiveSpeakersChanged → LayoutEngine.update_speakers()
                        → SubscriptionManager.compute_subscriptions(layout, bandwidth)

ConnectionQualityChanged → BandwidthController.update()
                           → SubscriptionManager.compute_subscriptions(layout, bandwidth)

UI: setCurrentPage(3) → LayoutEngine.set_current_page(3)
                        → SubscriptionManager.compute_subscriptions(layout, bandwidth)
```

API LiveKit utilisée: `RemoteTrackPublication::set_subscribed(bool)` et `set_video_quality()` (existantes dans SDK 0.7.32).

#### Modifications UDL

```
dictionary SubscriptionStats {
    u32 subscribed_high;
    u32 subscribed_low;
    u32 unsubscribed;
    u32 screen_shares;
};

SubscriptionStats get_subscription_stats();
```

#### Impact bande passante

Meeting 20 participants, page_size=4:
- Sans Phase 4: 20 × 1.5 Mbps = **30 Mbps**
- Avec (Full): 4 HIGH + 8 LOW = **8.4 Mbps** (-72%)
- Avec (ReducedVideo): 4 LOW = **1.2 Mbps** (-96%)

#### Tests

- Matrice complète: chaque combinaison visibilité × bandwidth mode
- Screen share override: toujours HIGH sauf AudioOnly
- Anti-jitter unsubscribe: encore souscrit à 1.5s, unsubscribed à 2s
- Anti-jitter quality: HIGH maintenu 5s, LOW à 5s
- Subscribe immédiat: 0 délai quand visible
- Grand groupe: 100 participants → 12 tracks actives (4 HIGH + 8 LOW)
- Transition bandwidth: Full→AudioOnly→Full mid-call

### 5a. #197 — Chiffrement des messages chat

**Fichier:** `crates/visio-core/src/chat.rs`
**Dépendance:** `aes-gcm` + `hkdf` (RustCrypto, pure Rust)

#### Dérivation de clé

```rust
fn derive_chat_key(room_token: &str) -> [u8; 32] {
    // HKDF-SHA256, salt: b"visio-chat-v1", info: b"aes-256-gcm"
}
```

Salt versionné (`v1`) pour migration future. Clé dérivée une fois au `connect()`.

#### Format message chiffré

```
[1 byte: version=0x01] [12 bytes: nonce] [N bytes: ciphertext+tag]
```

Encodé en base64 pour le transport via Stream API `lk.chat`.

#### Fallback rooms mixtes

- Message sans version byte 0x01 → texte clair, affiché tel quel
- Déchiffrement échoué → "[Message chiffré illisible]" avec flag `decryption_failed`
- UI: icône cadenas sur messages chiffrés, avertissement pour messages en clair

#### Modifications UDL

```
dictionary ChatMessage {
    // ... champs existants ...
    boolean encrypted;
    boolean decryption_failed;
};
```

#### Tests

- Round-trip: chiffrer → déchiffrer → texte identique
- Mauvaise clé: échec propre
- Message en clair: détecté, affiché tel quel
- Version byte inconnu: traité comme non-déchiffrable
- Messages longs (2000 chars): overhead < 3000 bytes

### 5b. #192 — Feature flags (Unleash)

**Nouveau module:** `crates/visio-core/src/features.rs`

#### FeatureService

```rust
pub struct FeatureService {
    proxy_url: Option<String>,
    flags: Arc<RwLock<HashMap<String, bool>>>,
    defaults: HashMap<String, bool>,
    refresh_interval: Duration,  // 60s
}
```

#### Defaults compilés

```rust
("background_blur", true), ("screen_share", true), ("pip", true),
("chat_encryption", false), ("speaker_mode", true), ("smart_subscriptions", true),
("oidc_auth", false)  // rollout progressif, remplace le cfg!(feature) compile-time à terme
```

Note: aujourd'hui l'OIDC est un feature flag Cargo compile-time (`cfg!(feature = "oidc")`). Le flag runtime `oidc_auth` permettra d'activer/désactiver l'OIDC par instance via le proxy Unleash sans recompiler. La logique de check deviendra: `is_oidc_enabled() = cfg!(feature = "oidc") && feature_service.is_enabled("oidc_auth")` — les deux conditions doivent être vraies (le code doit être compilé ET le flag runtime activé).

#### Lifecycle

1. Init (Phase 3 de #195): charge defaults, fetch proxy (timeout 3s, non-bloquant)
2. Refresh: `tokio::interval` 60s, GET sur proxy Unleash
3. API: `is_enabled("name") -> bool` — cache, fallback default

Client minimal (pas de dépendance Unleash). Le protocole est un GET JSON simple:
```json
{"toggles": [{"name": "chat_encryption", "enabled": true}]}
```

#### Modifications UDL

```
boolean is_feature_enabled(string feature_name);
void set_feature_flags_url(string? url);
```

#### Tests

- Pas de proxy → defaults
- Proxy répond → cache mis à jour
- Proxy injoignable → defaults maintenus
- Feature inconnue → false

## Contraintes

- Aucune dépendance serveur Meet — tout est côté client
- Rust edition 2024, `#[unsafe(no_mangle)]`
- UniFFI-compatible pour l'API publique de visio-core
- Android min SDK 26, iOS deployment target 16.0
- LiveKit SDK pinned =0.7.32
- Pas de cap codé en dur sur le nombre de participants
